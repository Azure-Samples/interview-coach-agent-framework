## What we are doing

Prepare the environment for a local .NET application that calls a model in Foundry. The starter itself does not provision cloud resources. Beginning with the first coach, Aspire can provision a Foundry resource and model deployment.

## Why readiness comes first

A missing SDK is not an agent problem. Neither is the wrong tenant, an unavailable model, or exhausted quota. Confirm these boundaries now so you can attribute later failures to the right component.

**Cloud resources and model usage can cost money, even when the application runs locally.** Do not use a shared or production resource group for a practice run.

## How and where

### 1. Check local tools

Use your terminal to confirm:

```sh
dotnet --version
docker info
aspire --version
az version
```

You need .NET 10, a running compatible container engine, the Aspire CLI, and the Azure CLI. Use VS Code with C# Dev Kit or Visual Studio. Start Docker before later lessons introduce the Cosmos emulator and MarkItDown.

If a command is missing, follow the official installation instructions for [.NET](https://dotnet.microsoft.com/download/dotnet/10.0), [Aspire](https://aspire.dev/get-started/install-cli/), or [Azure CLI](https://learn.microsoft.com/cli/azure/install-azure-cli). Do not replace the workshop's package versions with newer examples from unrelated tutorials.

### 2. Sign in and select the intended subscription

```sh
az login
az account show --query "{subscription:name, subscriptionId:id, tenant:tenantId}" --output table
```

For multiple tenants, use `az login --tenant YOUR_TENANT_ID`. If needed, select a subscription with `az account set --subscription YOUR_SUBSCRIPTION_ID`. Replace placeholders before running commands; do not paste account details into this site.

### 3. Check model access before starting lesson 03

The reference configuration requests `gpt-5-mini`, version `2025-08-07`, format `OpenAI`, and `GlobalStandard` capacity `100`. These are the sample's requested values, **not a guarantee of availability or an appropriate allocation for your subscription**.

Check the current [Foundry model availability](https://learn.microsoft.com/azure/ai-foundry/openai/concepts/models) and [quota guidance](https://learn.microsoft.com/azure/ai-foundry/openai/quotas-limits). Ask your subscription owner about the permitted region, deployment capacity, and provisioning permissions. Update `apphost.settings.json` only with values that are valid for your environment.

Record the intended subscription, region, resource group, model, and cleanup owner in your private notes. If you cannot obtain model access, you can read the course and run the agentless starter, but you cannot honestly complete the Foundry-backed exercises.

### 4. Understand what starts when

| Checkpoint | Local services | Cloud interaction |
| --- | --- | --- |
| 02 | UI and agent service shell | None |
| 03–04 | UI and agent service | Foundry provisioning/model calls |
| 05 | Add InterviewData MCP and Cosmos emulator | Foundry model calls |
| 06 onward | Add MarkItDown container | Foundry model calls |

The root `apphost.cs` is the local entry point. `azure.yaml` uses the project-based AppHost for optional deployment; that is a separate operation.

## See it work

You can identify the installed SDK, confirm that the container engine responds, and state which subscription would receive resources. You have checked model availability and permissions, rather than assuming an Azure sign-in grants them.

No model call is required at this checkpoint.

## Make it yours

Explain to a teammate why `aspire start` can incur cloud costs while the UI still runs on localhost. Identify the first lesson where that matters.

## If you get stuck

<Hint title="Authentication and authorization are different">
`az login` proves an identity. It does not prove that identity can provision a model deployment or use it. Inspect the precise error and the relevant resource scope rather than replacing identity-based authentication with a hard-coded key.
</Hint>

<Hint title="Container startup is separate from Foundry">
The later Cosmos emulator is a container with platform and resource requirements. A healthy model endpoint does not fix a container that cannot start. Check Aspire resource logs and Docker first.
</Hint>

## Carry forward

Download the starter next. Keep a resource inventory as you work. `aspire stop` stops local orchestration; it is not a cloud teardown command. The [deployment lab](../../resources/deployment/) explains cleanup boundaries, including resources provisioned during local runs.
