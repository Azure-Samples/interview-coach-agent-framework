Keep the repository's pinned package versions. The completed example uses a local Cosmos emulator and a MarkItDown container.

## Sign in to an Azure environment

To complete this workshop you will need to create Microsoft Foundry resources. So your account in your Azure subscription will need permissions to do that. In addition your account will need access to specific regions where the models can be deployed to with appropriate capacity.

You will need confirm permission to provision resources and call the model, make sure there is sufficient model quota, and who will handle cleanup (because you don't want this hanging around after).

This sounds worse than it is, stick to what we outline before and you _should_ be fine.

Signing in authenticates you; resource permissions need their own approval. Follow the steps below to sign in:

<Tabs syncKey="shell">
<TabItem label="Bash">

```bash
az login
subscriptionId=$(az account show --query id --output tsv)
az account show --subscription "$subscriptionId" --query "{subscription:name, subscriptionId:id, tenant:tenantId}" --output table
```

</TabItem>
<TabItem label="PowerShell">

```powershell
az login
$subscriptionId = az account show --query id --output tsv
az account show --subscription "$subscriptionId" --query "{subscription:name, subscriptionId:id, tenant:tenantId}" --output table
```

</TabItem>
</Tabs>

Check the displayed tenant and subscription before continuing. Keep account details private.

The `subscriptionId` variable lasts for this terminal session. If the selected subscription isn't the approved one, list your subscriptions and select it below. Replace `YOUR_SUBSCRIPTION_ID` with its ID, then rerun the variable assignment and account-details command above.

<Tabs syncKey="shell">
<TabItem label="Bash">

```bash
az account list --output table
az account set --subscription "YOUR_SUBSCRIPTION_ID"
```

</TabItem>
<TabItem label="PowerShell">

```powershell
az account list --output table
az account set --subscription "YOUR_SUBSCRIPTION_ID"
```

</TabItem>
</Tabs>

## Clone the finished app

We've designed this workshop so you can run the code locally but follow the instructions on this website. So lets first test out that all the prerequisties are installed by running the final version of interview coach application.

Clone this finished example once. Keep `interview-coach-example` for trying the app and looking up completed code. In Chapter 1, we'll download the starter once into a separate `interview-coach-lab` folder beside it, then keep editing that same learner project for the rest of the workshop.

1. Choose a parent directory for your workshop folders. Clone the repository into a new `interview-coach-example` folder:

   <Tabs syncKey="shell">
   <TabItem label="Bash">

   ```bash
   git clone https://github.com/codemillmatt/interview-coach-agent-framework.git interview-coach-example
   cd interview-coach-example
   ```

   </TabItem>
   <TabItem label="PowerShell">

   ```powershell
   git clone https://github.com/codemillmatt/interview-coach-agent-framework.git interview-coach-example
   cd interview-coach-example
   ```

   </TabItem>
   </Tabs>

2. Check out the workshop's pinned tag. This selects the example version used to generate our checkpoints (that makes it easy to troubleshoot later if we need to):

   <ShellCommands command={`git checkout --detach ${labs.sourceTag}`} />

3. Azure CLI supplies your sign-in, but Aspire still needs to know where it should provision resources. Replace `YOUR_APPROVED_AZURE_REGION` with a region that supports the configured model. Use an existing approved resource group if you were given one; otherwise replace `YOUR_NAME` with something that makes the new group easy to identify.

   <Tabs syncKey="shell">
   <TabItem label="Bash">

   ```bash
   subscriptionId=$(az account show --query id --output tsv)
   tenantId=$(az account show --query tenantId --output tsv)
   location="YOUR_APPROVED_AZURE_REGION"
   resourceGroup="rg-interview-coach-YOUR_NAME"

   aspire secret set "Azure:SubscriptionId" "$subscriptionId" --apphost ./apphost.cs
   aspire secret set "Azure:TenantId" "$tenantId" --apphost ./apphost.cs
   aspire secret set "Azure:Location" "$location" --apphost ./apphost.cs
   aspire secret set "Azure:ResourceGroup" "$resourceGroup" --apphost ./apphost.cs
   aspire secret set "Azure:CredentialSource" "AzureCli" --apphost ./apphost.cs
   ```

   </TabItem>
   <TabItem label="PowerShell">

   ```powershell
   $subscriptionId = az account show --query id --output tsv
   $tenantId = az account show --query tenantId --output tsv
   $location = "YOUR_APPROVED_AZURE_REGION"
   $resourceGroup = "rg-interview-coach-YOUR_NAME"

   aspire secret set "Azure:SubscriptionId" "$subscriptionId" --apphost ./apphost.cs
   aspire secret set "Azure:TenantId" "$tenantId" --apphost ./apphost.cs
   aspire secret set "Azure:Location" "$location" --apphost ./apphost.cs
   aspire secret set "Azure:ResourceGroup" "$resourceGroup" --apphost ./apphost.cs
   aspire secret set "Azure:CredentialSource" "AzureCli" --apphost ./apphost.cs
   ```

   </TabItem>
   </Tabs>

   These values are stored in the example's local AppHost user secrets, outside the repository. The learner project will have its own configuration and reuse this model. Aspire creates the named resource group if it does not exist and your account has permission. If your organization does not allow resource-group creation, use an existing group supplied by your administrator.

4. Open this folder in your editor.

In the root `apphost.settings.json`, review these existing values, keeping the other settings:

```json
{
  "AgentMode": "HandOff",
  "LlmProvider": "MicrosoftFoundry",
  "MicrosoftFoundry": {
    "DeploymentName": "gpt-5-mini",
    "ModelVersion": "2025-08-07",
    "ModelFormat": "OpenAI",
    "SkuName": "GlobalStandard",
    "SkuCapacity": 100
  }
}
```

Confirm that this model, version, SKU, and capacity are available and approved in your chosen environment. (The best way may be to just try what we have above and see if it works.)

:::caution[Starting the example can create billable Azure resources]
The next command can provision a Foundry resource and model deployment. Model calls also incur usage charges. Record the resources created for this folder, and review provisioning prompts against your approval. Stopping Aspire leaves cloud resources in place. Remove only resources you own and are authorized to delete.
:::

We'll build and run the application. From the `interview-coach-example` root:

```bash

aspire start --apphost ./apphost.cs
```

</TabItem>
<TabItem label="PowerShell">

```powershell
dotnet build InterviewCoach.slnx

```

</TabItem>
</Tabs>

Open Aspire's printed dashboard URL. Once the services are ready, open the `webui` endpoint.

## Try a short interview

```text
Help me prepare for a cloud solution architect interview. Ask one question
at a time. I'll provide a fictional resume and job description.
```

<p>When asked, download <a href={siteLink('samples/resume-peter-parker.pdf')}>Peter Parker resume</a> and <a href={siteLink('samples/jd-cloud-solution-architect.pdf')}>cloud solution architect job description</a> locally and then upload them to the conversation. The parser container needs reachable URLs, the localhost workshop preview may be inaccessible to it, so we'll provide the files.</p>

Give one short, fictional behavioural answer, for example:

```text
Our practice deployment failed after a configuration change. I compared
the settings, reverted the change, and added a startup check.
```

Ask `Move on to technical questions.`, answer one question, then send `Finish the interview now and save a short summary.`

Look for feedback tied to your answers and a final summary. Exact wording will vary. We'll inspect tool calls and saved records in the chapters where we build them.

## Keep the model for your learner project

We'll keep using this Foundry account and its model deployment throughout the workshop. Find its account name and resource group:

<Tabs syncKey="shell">
<TabItem label="Bash">

```bash
az cognitiveservices account list --query "[?kind=='AIServices'].{Account:name,ResourceGroup:resourceGroup,Location:location}" --output table
```

</TabItem>
<TabItem label="PowerShell">

```powershell
az cognitiveservices account list --query "[?kind=='AIServices'].{Account:name,ResourceGroup:resourceGroup,Location:location}" --output table
```

</TabItem>
</Tabs>

Use the account in the resource group you configured above. Replace the two placeholders to list its deployments:

<Tabs syncKey="shell">
<TabItem label="Bash">

```bash
az cognitiveservices account deployment list --name "YOUR_ACCOUNT_NAME" --resource-group "YOUR_RESOURCE_GROUP" --query "[].{Deployment:name,Model:properties.model.name,State:properties.provisioningState}" --output table
```

</TabItem>
<TabItem label="PowerShell">

```powershell
az cognitiveservices account deployment list --name "YOUR_ACCOUNT_NAME" --resource-group "YOUR_RESOURCE_GROUP" --query "[].{Deployment:name,Model:properties.model.name,State:properties.provisioningState}" --output table
```

</TabItem>
</Tabs>

Keep the account name, resource group, and **Deployment** value for Chapter 2. The example normally names the Azure deployment `chat`; the **Model** column names the model running inside it. We'll reuse the deployment without changing its model or capacity.
