## Read the completed graph

The usual interview follows the specialist chain. Triage can also select any specialist, and each specialist can return to triage for a changed request.

<ConceptDiagram kind="handoffs" />

Why keep these eleven edges? Direct phase transitions avoid asking triage to choose again after every specialist. Return routes still let the user change direction. The graph supports both ordinary progress and an early finish.

A hub-only graph would add a triage decision between phases. A chain without return routes would restrict changed requests. Neither design is universally wrong. Choose routes for the interactions the application needs.

The graph permits transfers without forcing a fixed sequence. If the next operation must always be the same, ordinary code or a sequential workflow may be simpler.

## Keep the response language across handoffs

The conversation and its documents can use different languages. A specialist may follow the language of a resume or job description instead of the user's messages. This can happen after a handoff, even when the previous specialist used the user's language.

Before adding a policy, try the `07-interviewers` checkpoint from Chapter 11 in WebUI. Choose a conversational language and provide fictional resume and job description text in another language. English, Korean, Spanish, Japanese, or any other language supported by your model can be either the conversational or document language. Ask for behavioural practice, then technical practice, and note the response language. A language change is possible, not required; model responses vary.

We'll add a shared policy at the agent factory so every specialist receives the same rules. An explicit response-language request takes priority. Otherwise, use the user's conversational language, retaining the established language for short or ambiguous replies. Documents and tool results provide interview context, not a language preference.

The policy has no list of allowed languages; the model's language capabilities still determine which languages work well. Instructions guide responses, but they do not guarantee compliance.

The policy applies to user-facing responses. Tool names, structured arguments, and stored source documents keep their original meaning and format.

### Check the language policy

Select **New chat** and repeat your mixed-language case using the updated project. Write your conversational messages in your chosen language and provide fictional documents in a different language. Repeat with the languages reversed or with another pair if you can assess both. Neither English nor Korean has a special role.

Check these behaviours:

| Interaction | Expected observation |
| --- | --- |
| Provide documents in a different language from your messages, then move from intake to interview practice. | Replies follow your conversational language across specialist handoffs. |
| Reply with a number or a short, language-ambiguous acknowledgement such as `OK`. | The established response language is retained. |
| Explicitly request a different response language, including one different from both the conversation and the documents. | Replies use the requested language, including after the next handoff. |
| Inspect the saved resume/job description text in Cosmos Data Explorer and the tool calls in execution telemetry. | Source text is preserved; tool names and structured fields are not translated. User-facing feedback can use the chosen response language. |

Record your language choices and what happened. If a response breaks the policy, keep the failing turn and inspect the active agent's instructions and conversation context. A successful run is evidence for that case, not proof that every model and language pair behaves the same way.
