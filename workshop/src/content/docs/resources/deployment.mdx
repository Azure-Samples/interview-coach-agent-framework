## What we are doing

Deploy the existing Aspire application to Azure Container Apps. This is an optional extension after the local capstone, not a requirement to finish the workshop.

The .NET service continues to run the agents. Foundry continues to provide the model. This operation does not move the agents into Foundry Agent Service.

## Why deployment is a separate decision

Local success does not settle identity, access restrictions, public endpoints, retention, cost, or production readiness. In particular, this sample exposes development interfaces and keeps uploads in process memory. Do not treat it as a production service merely because it can be deployed.

The commands below are the repository's deployment path. Exact permissions, model availability, identity assignments, and cleanup must be checked for your subscription and current Azure tooling. No live deployment was performed to build this static workshop.

## How and where

### 1. Inspect the deployment entry point

Open `azure.yaml` in your completed project. Its service points to `src/InterviewCoach.AppHost/InterviewCoach.AppHost.csproj` with `host: containerapp`.

Review that AppHost's configuration as well as your root local settings. They are separate entry points. Confirm your intended model, mode, tenant, region, capacity, and dedicated resource group before provisioning.

### 2. Prepare an isolated environment

Install the [Azure Developer CLI](https://learn.microsoft.com/azure/developer/azure-developer-cli/install-azd), then from the completed project root:

```sh
azd auth login
azd init
```

Choose a new, clearly named development environment. Inspect `azd env get-values` locally to confirm the environment; its output can contain sensitive configuration, so do not paste it into the workshop or a public issue.

Check current [Aspire deployment guidance](https://learn.microsoft.com/dotnet/aspire/deployment/azure/aca-deployment) and [Foundry authorization guidance](https://learn.microsoft.com/azure/ai-foundry/concepts/rbac-azure-ai-foundry). Have the subscription owner confirm required roles and scope rather than granting broad permanent permissions.

### 3. Provision only when you are ready for the cost

```sh
azd up
```

Review the selected subscription, location, and proposed resource ownership before accepting prompts. Do not run this against a shared production environment.

## See it work

Inspect deployed resource health and identity-related errors, then perform the same short interview as the local capstone. Confirm that the UI reaches the agent and that both MCP services can reach their dependencies.

Review which endpoints are public and which development interfaces are exposed. Restrict access before allowing anyone else to use the deployment.

## Make it yours

Write a production-readiness list for this specific app: access control, per-user data authorization, upload storage/retention, tool permissions, retries/timeouts, logging of personal data, and cost limits. Separate an instruction change from a control that must exist in code or infrastructure.

## If you get stuck

Do not repeatedly provision new environments to fix one failure. Read the failing resource and operation, then distinguish model quota, role assignment, image startup, service connectivity, and application errors.

## Carry forward: clean up deliberately

For resources owned by the selected `azd` environment, review the removal prompt:

```sh
azd down
```

Avoid `--force --purge` as a casual workshop default. Confirm scope and retention first.

Resources provisioned by a previous **local Aspire run** may not belong to this `azd` environment. Compare your resource inventory with what remains in the subscription and remove only resources dedicated to your workshop. `aspire stop` does not remove cloud resources.
